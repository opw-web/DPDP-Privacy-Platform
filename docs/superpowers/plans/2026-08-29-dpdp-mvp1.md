# DPDP Platform MVP 1 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` to implement this plan task-by-task.

**Goal:** Build MVP 1 of a DPDP Act 2023 / DPDP Rules 2025 compliance platform — multi-tenancy, auth and RBAC, an append-only hash-chained audit log, read-only discovery connectors, deterministic identity resolution, the Record of Processing registers, and a Data Principal portal.

**Architecture:** Two independent projects. `dpdp-platform/` is a NestJS 10 + Prisma 5 + PostgreSQL 16 backend with a React 18 + Vite 5 SPA carrying two route trees (fiduciary `/app/*`, principal `/me/*`), plus Redis/BullMQ for sync jobs. `demo-company-server/` is a wholly separate Fastify 4 + better-sqlite3 service that impersonates a fake business's four unconnected systems. Neither project may import from or name the other.

**Tech Stack:** TypeScript 5.5 strict, Node 20, NestJS 10, Prisma 5, PostgreSQL 16, BullMQ 5 + Redis 7, argon2id, React 18, Vite 5, Tailwind 3 + shadcn/ui, TanStack Query 5 + Table 8, react-hook-form + zod, Fastify 4 + better-sqlite3, Docker Compose v2.

**Spec:** `DPDP_MVP1_FOUNDATION_AND_DISCOVERY.md` (1153 lines, repo root) — the binding authority. This plan argues from it; where they differ, the spec wins.
**Companion:** `DPDP_COMPLIANCE_CHECKLIST.md` — the checklist IDs (LB-02, GO-03, SE-03, RT-04 …) cited throughout.

## Global Constraints

Verbatim from spec §1 and §2.1. **Every task's requirements implicitly include this section.**

1. **Read-only external access.** The platform never writes to a connected system. The HTTP client physically refuses any method other than GET — an interceptor that throws before a socket opens, not a code-review convention.
2. **Two independent codebases.** `dpdp-platform/` and `demo-company-server/` have zero source-code dependency either way. Deleting `demo-company-server/` must leave the platform fully buildable and testable. No npm workspace, two separate lockfiles, and no environment variable in the production app names the demo. There is deliberately no `DEMO_SERVER_URL`.
3. **Multi-tenant from line one.** Every business is an `Organization`; every business-data row carries `organizationId`; isolation is enforced in **one Prisma client extension**, never by remembering a `where` clause. No service passes `organizationId` manually.
4. **Nothing legal is hard-coded.** No `90`, `72`, `48`, `30` or `3 years` as a bare literal in application code. Legal periods are configuration or database columns, always with a cited source.
5. **Everything is auditable.** Every state change writes an append-only `AuditEvent`, protected by a database trigger that rejects UPDATE and DELETE, and hash-chained per organization. `AuditService.record()` is the only writer to that table.
6. **Reversible identity.** A merge is a link, never a destruction. Every merge can be undone. Source records are never mutated or deleted.
7. **Timezone discipline.** `timestamptz` in UTC everywhere; convert to the organization's timezone exactly once, at the render boundary.
8. **The platform never concludes.** It records a human's determination, who made it and when. No screen may claim the company "is compliant" — the language is "supports", "evidences", "tracks".

**Locked stack — do not substitute (spec §2.1, lines 54–75).** TypeScript 5.5+ with `strict` and `noUncheckedIndexedAccess` on; Node 20 LTS; NestJS 10; Prisma 5.x; PostgreSQL 16; BullMQ 5 + Redis 7; class-validator + class-transformer; `@nestjs/swagger` served at `/api/docs`; nestjs-pino (JSON logs, request-id correlation); argon2id; React 18 + Vite 5; react-router-dom 6; Tailwind 3 + shadcn/ui + lucide-react; TanStack Query 5; react-hook-form + zod; TanStack Table 8; papaparse (frontend only); Fastify 4 + better-sqlite3 (demo server only); Docker Compose v2; MailHog. **Package manager npm, two separate lockfiles, no root workspace.**

**Locked ports (spec §2.3).** Backend API 4000 · frontend dev server 5173 · demo company server 5001 · PostgreSQL 5432 · Redis 6379 · MailHog SMTP/UI 1025/8025.

**Forbidden in identity resolution (spec §4.4, lines 776–777).** Matching on name alone, name + city, fuzzy email similarity, or any probabilistic model. `nameKey` is a supporting signal only, never a match rule. Do **not** strip Gmail dots or `+tags` from emails.

**Counts stated in this plan are NOT authoritative.** Where a task references a fenced block in the spec (action names, permission codes, field lists), transcribe every entry in that block verbatim and count from the block itself. Two counts asserted in earlier drafts of this plan were wrong — audit actions are 35, not 33; permission codes are 22, not 23. The spec's block always wins over this plan's prose, and a mismatch is worth escalating rather than silently reconciling.

**Enforcement style.** Permission checks are `@RequirePermission('CAN_X')`. The string `if (user.role === 'DPO')` — or any role-name comparison used for authorization — must not appear anywhere in the codebase.

**Environment (already prepared; do not re-install).**

**Commit discipline.** Small, frequent commits with conventional-commit subjects. Commit only files your task owns. Never commit `.env`, `node_modules/`, `dist/`, or `demo-company-server/data/*.sqlite`.

## Risks and rulings taken up front

- **Node 22 is on PATH; the spec locks Node 20.** Ruling: pin 20 via nvm; every subagent sources it. Cost if wrong: native modules built against 22 fail in the Node 20 container — caught by the Docker build.
- **Docker access via `sg docker -c`** rather than sudo, so no password reaches a subagent prompt. Cost if wrong: nothing; falls back to sudo.
- **No git worktree**; work happens on branch `mvp1-foundation` in the main checkout. A fresh repo with no other branches makes a worktree pure overhead and Docker bind mounts are simpler from one path.
- **7 GB RAM, ~4 GB already in use.** Ruling: run the frontend dev server on the host during development; the compose `frontend` service exists for the clean-clone check (Check 24) and is built only there.
- **`graphify update .`** is run by the orchestrator at phase boundaries (after Tasks 8, 22 and 30), not after every task.

**Interfaces:**
- Produces: `AuditService.record(tx, input)` where `input` is `{ action: AuditAction; resourceType: string; resourceId?: string; subjectPrincipalId?: string; metadata?: Record<string, unknown>; ipAddress?: string; userAgent?: string }`. Actor fields come from `TenantContext`, never from the caller. **It runs inside the caller's transaction** — the `tx` parameter is a Prisma transaction client.
- Produces: `AuditAction` — a string-literal union of exactly the action names in the fenced block at spec lines 880–891, transcribed verbatim. There are 35 distinct names; the spec itself states no count, and an earlier draft of this plan miscounted them as 33.
- Produces: `ReferenceService.next(name)` allocating the next `Counter` value for the current org under `SELECT … FOR UPDATE`, and `ReferenceService.nextPrincipalReference()` formatting `DP-000123` (six digits, zero-padded).
- Consumes: `TenantContext` (Task 3), `PrismaService` (Task 2).

**Requirements:**
- Sequence allocation: `SELECT value FROM "Counter" WHERE ... FOR UPDATE` inside the transaction, then increment. Concurrent writers must serialize — no gaps, no duplicates, starting at 1 per organization.
- `hash = sha256(previousHash + sequence + action + resourceId + canonicalJson(metadata) + createdAt)`. `previousHash` is the hash of the immediately preceding event for the same organization (`null`/empty for sequence 1). `canonicalJson` sorts object keys recursively and is deterministic across runs — write it yourself and unit-test it, do not use `JSON.stringify` on arbitrary objects.
- `AuditService` is the **only** code path that inserts into `AuditEvent`. Add a lint-visible comment saying so.
- Metadata must never contain a plaintext credential, password hash, or token.

**Tests:**
- `canonical-json.spec.ts`: key order independence, nested objects, arrays preserved in order, `undefined` handling, stability across two calls.
- `audit.e2e-spec.ts`: 50 events written concurrently across 10 transactions produce sequences 1..50 with no gaps and no duplicates; each event's `previousHash` equals the prior event's `hash`; a chain-verification helper walking the org's events end to end reports intact; two organizations maintain independent sequences both starting at 1.

**Done when:** the concurrency test passes repeatably and chain verification is green.

**Commit:** `feat(audit): add hash-chained append-only AuditService and reference counters`
