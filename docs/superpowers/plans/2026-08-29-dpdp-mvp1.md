## Context

The repository currently contains **no code** — only three specification documents, a graphify knowledge graph, and journal tooling. `DPDP_MVP1_FOUNDATION_AND_DISCOVERY.md` is a complete, self-contained build document for MVP 1 of a B2B SaaS platform that helps Indian businesses operate their obligations under the Digital Personal Data Protection Act 2023 and the DPDP Rules 2025.

MVP 1 builds four things: the plumbing (multi-tenancy, auth, permission-based access control, an append-only audit log the database itself protects), discovery (read-only connectors, sync, field mapping, deterministic identity resolution), the Record of Processing (purposes with lawful basis, processors, recipients, transfers, retention, security measures), and the evidence floor (access log, audit chain, inventory exports). There is no consent collection, notice builder, rights request, breach handling or retention execution — those are MVP 2, and every one of them depends on MVP 1 being right.

The intended outcome is the spec's own definition of done (spec §7): `docker compose up` from a clean clone brings up the stack; an admin declares purposes with explicit lawful bases, connects four read-only demo APIs, maps fields, registers processors and recipients, and syncs; 500 scattered records become 327 unique Data Principals with 4 ambiguous pairs queued for human review, 2 same-named strangers kept apart, 12 field conflicts surfaced in amber and 6 under-18 records flagged; every value names the systems it came from; a Data Principal logs into her own portal and sees exactly her data and nobody else's; and all 24 evaluation checks in spec §6 pass.

**Execution model (per the user's instruction):** the orchestrator (Opus, medium effort) writes **no application code**. Every line of code is written by dispatched Sonnet (medium effort) implementer subagents under `superpowers:subagent-driven-development` — fresh implementer per task, task review after each, fix loop, broad final review. The orchestrator handles only: host environment setup requiring sudo, git bookkeeping, the ledger, dispatch briefs, review packages, and rulings.

## Global Constraints

Copied verbatim from spec §1 "Non-negotiable project rules" and §2.1. **Every task's requirements implicitly include this section.**

1. **Read-only external access.** The platform never writes to a company's connected systems. The HTTP client physically refuses any method other than GET — an interceptor that throws before a socket opens, not a code-review convention.
2. **Two independent codebases.** `dpdp-platform/` and `demo-company-server/` have zero source-code dependency either way. Deleting `demo-company-server/` must leave the platform fully buildable and testable. **No npm workspace, two separate lockfiles, and no environment variable in the production app names the demo.** There is deliberately no `DEMO_SERVER_URL`.
3. **Multi-tenant from line one.** Every business is an `Organization`; every business-data row carries `organizationId`; isolation is enforced in **one Prisma client extension**, never by remembering a `where` clause. No service passes `organizationId` manually.
4. **Nothing legal is hard-coded.** No `90`, `72`, `48`, `30` or `3 years` as a bare literal in application code. Legal periods are configuration or database columns, always with a cited source.
5. **Everything is auditable.** Every state change writes an append-only `AuditEvent`, protected by a database trigger that rejects UPDATE and DELETE, and hash-chained per organization. `AuditService.record()` is the only writer.
6. **Reversible identity.** A merge is a link, never a destruction. Every merge can be undone. Source records are never mutated or deleted.
7. **Timezone discipline.** `timestamptz` in UTC everywhere; convert to the organization's timezone exactly once, at the render boundary.
8. **The platform never concludes.** It records a human's determination, who made it and when. No screen may claim the company "is compliant" — the language is "supports", "evidences", "tracks".

**Stack (locked — do not substitute), spec §2.1:** TypeScript 5.5+ `strict` + `noUncheckedIndexedAccess`; Node 20 LTS; NestJS 10; Prisma 5.x; PostgreSQL 16; BullMQ 5 + Redis 7; class-validator + class-transformer; `@nestjs/swagger` at `/api/docs`; nestjs-pino (JSON, request-id correlation); argon2id; React 18 + Vite 5; react-router-dom 6; Tailwind 3 + shadcn/ui + lucide-react; TanStack Query 5; react-hook-form + zod; TanStack Table 8; papaparse (frontend); Fastify 4 + better-sqlite3 (demo server); Docker Compose v2; MailHog. **Package manager: npm.**

**Ports (locked), spec §2.3:** backend 4000, frontend 5173, demo server 5001, Postgres 5432, Redis 6379, MailHog 1025/8025.

**Forbidden in identity resolution (spec §4.4):** matching on name alone, name + city, fuzzy email similarity, or any probabilistic model. `nameKey` is a supporting signal only, never a match rule. Do **not** strip Gmail dots or `+tags` from emails.

**Enforcement style:** `@RequirePermission('CAN_X')`. The string `if (user.role === 'DPO')` must not appear anywhere in the codebase.

**Environment decisions made for this build:**
- Node 20 LTS pinned via nvm 0.39.7 (`nvm use 20`). Subagents must `source ~/.nvm/nvm.sh && nvm use 20` before any npm/node command.
- Docker Engine + Compose plugin installed via apt; **all docker commands run through sudo** (user chose this over re-login). Orchestrator handles sudo; subagents are told to prefix `sudo` and are never given the password — the orchestrator pre-authorises sudo for the session.
- Work happens on branch `mvp1-foundation` in a freshly `git init`-ed repo at the project root (not a worktree — Docker bind mounts and a fresh repo make a worktree pure overhead).

### Task detail highlights

Full requirements travel in the per-task brief; these are the points where a reviewer will most often find a gap, called out so the briefs carry them.

**Task 2** — The Prisma schema is spec lines 176–579, transcribed exactly (all enums, all models, all `@@unique`/`@@index`). Migration two is spec lines 583–606 verbatim as raw SQL: the partial unique index `identity_link_one_active`, the `audit_is_immutable()` trigger on both UPDATE and DELETE, the `processor_requires_contract` CHECK, `pg_trgm` and the two GIN trigram indexes. Done-when includes proving from `psql` that `UPDATE "AuditEvent" …` raises `AuditEvent rows are immutable`.

**Task 3** — Middleware puts `{organizationId, actorType, actorId}` into `AsyncLocalStorage`; a Prisma client extension injects `organizationId` into every `where` and every `create` for tenant-scoped models. `Permission` is the only exempt model. The gate: a two-org isolation test (Acme + Globex) that must pass before any later task is dispatched. A direct fetch of another org's row returns **404, not 403** — 403 confirms the row exists.

**Task 4** — `AuditService.record()` runs in the caller's transaction, takes `Counter('AUDIT')` with `SELECT … FOR UPDATE`, and stores `hash = sha256(previousHash + sequence + action + resourceId + canonicalJson(metadata) + createdAt)`. Canonical JSON means deterministic key ordering — a sorted-key serializer, not `JSON.stringify` on arbitrary objects. The 33 MVP 1 action names are spec lines 880–891.

**Task 7** — Masking happens in the **service layer, never in React** (`am**@gm***.com`, `+91 98****3210`), so an auditor cannot read real values from devtools. `ACCESS_LOG_RETENTION_DAYS` is read from config; the app **refuses to start** below 365 and says why. `PERSONAL_DATA_VIEWED` carries `subjectPrincipalId`.

**Task 8** — `lawfulBasis` is required with no default and no inference; `LEGITIMATE_USE` without a s.7 limb is a 400. A source named "Marketing Database" never gets a marketing purpose automatically. Unreviewed purposes carry an amber "Not yet reviewed" chip everywhere they appear.

**Task 10** — The generator is seeded and deterministic. Exact targets: 500 raw records, 327 distinct people, ~30 records with no email, ~25 with no phone, ~12 with a conflicting field, exactly 2 different people named "Rahul Verma", exactly 4 possible-duplicate pairs (same `nameKey` + same pincode, no shared email or phone), exactly 6 records with a `dob` under 18 (e-commerce only). The seven named personas (spec lines 939–947) must exist by name. The README carries the copy-paste endpoint table (lines 930–935) and the persona table. Anything other than GET returns 405; a wrong bearer key returns 401.

**Task 11** — Timeout 15 s; 3 retries with backoff 1 s / 3 s / 9 s on 5xx and network errors; **no retry on 4xx**. `discoverSchema()` reads one page, unions keys across the first 20 records, infers `string|number|boolean|date|null`, truncates samples to 40 chars, and re-scrubs stored samples when a field is later marked `containsPersonalData`. Pagination `?page=N&limit=M` until a short page, hard cap 500 pages then fail loudly. Log lines strip query params. A unit test must prove the request helper throws on `method: 'POST'` before a socket opens.

**Task 15** — Normalizers get unit tests **first**; the phone table at spec lines 755–763 is the fixture, including `98765 43210`, `+91-98765-43210`, `09876543210`, `919876543210`, `9876543210` → `+919876543210` and `123` → `null`. Email: trim → NFKC → lowercase, nothing else. `nameKey` = lowercase alphanumeric tokens sorted.

**Task 16** — The five rules in exact order, each unit-tested alone before any full sync: CUSTOMER_ID exact (gated on `isVerifiedCustomerId`) → EXACT; EMAIL exact → EXACT; PHONE exact → HIGH; supporting-signal (`nameKey` equal AND one of same postalCode / same DOB / same last-6 of phone) → POSSIBLE, score 0.5–0.8, **raise a candidate, do not link**; otherwise UNMATCHED → new principal. Conflict rule: rules 1–3 pointing at two different principals link to the higher-confidence one and raise a candidate against the other with evidence `{"conflict":"EMAIL→A, PHONE→B"}`.

**Task 17** — Assembly gathers ACTIVE-linked normalized records, groups by `(canonicalField, value)`, unions contributing `dataSourceIds`, marks `isPrimary` from the most recently synced record, and sets `conflict = true` on any field with more than one distinct value. Age: derive only from a mapped, present `DATE_OF_BIRTH`; otherwise `UNKNOWN`. Never infer age from purchase behaviour, product category or name.

**Task 18** — Job id `sync:{dataSourceId}`; a second trigger while one runs returns **409**. Repeatable jobs are registered on save for non-`MANUAL` frequencies (`*/15 * * * *`, `0 * * * *`, `0 2 * * *` in the org timezone), and a frequency change **removes the old repeatable job first**. Unchanged payload hash skips the rest of the pipeline — this is what makes re-running a sync a no-op.

**Task 22** — `/api/me/*` resolves the principal **from the token only**. No route under `/api/me` accepts an ID parameter. This is the single most important security decision in the portal, and the task's review must confirm it by inspection of the route definitions, not just by test.

**Task 30** — Runs all 24 checks in spec §6 against a live stack and writes a findings report. Checks that are *findings rather than bugs* (spec line 1130) are reported as such. This task fixes nothing; anything it finds routes back through the orchestrator as a fix dispatch.

## Verification

Per-task verification is the SDD loop: implementer runs its own tests, then a task reviewer gates spec compliance and quality against the brief and the review package.

End-to-end verification is spec §6 (lines 986–1144), run in full as Task 30 after a complete four-source sync. The load-bearing ones:

- **Check 1 (tenant isolation):** Globex rows never appear for Acme; direct fetch is 404.
- **Check 2 (detachable demo):** `grep -rn "demo-company-server\|demo_marketing\|localhost:5001" dpdp-platform/backend/src dpdp-platform/frontend/src` returns nothing, and both builds succeed with `demo-company-server/` moved to `/tmp`.
- **Check 3 (provably read-only):** the request helper throws on POST before a socket opens; the demo server's access log shows only GET across a full sync.
- **Check 4 (idempotent sync):** re-running all four syncs leaves `SourceRecord` and `DataPrincipal` counts unchanged; second job shows `recordsCreated = 0`.
- **Check 6/7 (327 ± 4 people, 4 pending candidates, exactly 2 Rahul Vermas):** the anti-over-merge gate.
- **Check 10 (≈12 conflicts surfaced in amber):** assembly collects rather than overwrites.
- **Check 13 (processor without contract):** rejected by the API *and* by the database constraint.
- **Check 15/16/17 (access log, immutability, gapless sequence):** backend refuses to start with `ACCESS_LOG_RETENTION_DAYS=90`; UPDATE and DELETE on `AuditEvent` both raise; sequence starts at 1 with no gaps.
- **Check 19 (IDOR):** Aman's token returns only Aman's values; an employee token on `/api/me/data` returns 401 on audience mismatch.
- **Check 22 (performance):** four-source sync of 500 records under 30 s; principal detail under 500 ms with fewer than 15 SQL queries.
- **Check 24 (clean clone):** `docker compose up --build` plus `npm run seed` gets to a logged-in admin in five minutes with no manual SQL.

Commands the orchestrator runs directly (they need sudo or the host toolchain): `sudo docker compose up -d`, `psql postgresql://dpdp:dpdp@localhost:5432/dpdp`, and the Check 2 grep and build.

## Risks and rulings taken up front

- **Node 22 is installed system-wide; the spec locks Node 20.** Ruling: pin 20 via nvm and require every subagent to `source ~/.nvm/nvm.sh && nvm use 20`. Cost if wrong: a subagent that forgets the source line builds against 22 and may produce native-module artefacts that fail in the Node 20 container — caught by the Docker build.
- **All docker commands run under sudo** (user's choice over re-login). Cost if wrong: container-created files under `pgdata` are root-owned; recoverable with `sudo chown`.
- **No git worktree; work happens on branch `mvp1-foundation` in the main checkout.** A fresh repo with no other branches makes a worktree pure overhead, and Docker bind mounts are simpler from one path. Cost if wrong: nothing to rebase against; the branch is the isolation.
- **7 GB RAM with ~4 GB already in use.** Postgres + Redis + MailHog + Nest + Vite will be tight. Ruling: run the frontend dev server on the host rather than in a container during development; the compose `frontend` service exists for the clean-clone check (Check 24) and is built only there.
- **`graphify update .` after code lands.** Per project CLAUDE.md the graph must be refreshed; the orchestrator runs it at phase boundaries (after tasks 8, 22 and 30) rather than after every task, since it is AST-only but not free.
