# DPDP Platform MVP 2 — Compliance Operations — Implementation Plan

> **REQUIRED SUB-SKILL:** `superpowers:subagent-driven-development`.
>
> **Execution model (binding, from the human partner's instruction):** the orchestrator is **Opus at medium effort** and **writes no code at all** — not a line, not a fix, not a router import, not a commit of its own authorship. Every file in this repository is written by a dispatched **Sonnet, medium-effort** implementer subagent. Implementers run **in parallel, four at a time**, in waves (see *Wave Discipline*). The orchestrator reads, dispatches, packages diffs, adjudicates review findings, rules on conflicts, and keeps the ledger.

## Context

`DPDP_MVP1_FOUNDATION_AND_DISCOVERY.md` is built, merged to `main`, and verified: 260 backend e2e tests, 147 frontend tests, 24/24 spec checks (`docs/EVALUATION_MVP1.md`). It gave the product a spine — multi-tenancy through a single Prisma client extension, an append-only hash-chained audit log behind a database trigger, GET-only connectors, deterministic identity resolution turning 500 raw records into 327 canonical Data Principals with lineage and conflict flags, a purpose register where every purpose already carries an explicit lawful basis, and the five compliance registers.

What MVP 1 does **not** do is *operate*. A company can see who it holds data about; it cannot yet tell those people what it holds, collect and evidence consent purpose by purpose, answer a rights request against a deadline it configured, protect a child by construction, erase without breaching the one-year retention floor, or run a breach against a live regulator clock with per-person delivery evidence behind every claim.

`DPDP_MVP2_COMPLIANCE_OPERATIONS.md` (1,225 lines, repo root) is the binding spec for that second half. **This plan argues from it; where they differ, the spec wins.** Its companion `DPDP_COMPLIANCE_CHECKLIST.md` supplies the IDs (NT-04, CN-09, CH-05, RT-11, RE-07, BR-14, EV-03…) cited throughout.

**Intended outcome:** the 34-step acceptance demonstration in spec §7 (lines 1167–1224) runs end to end on a freshly seeded database with no SQL and no code changes, and all 36 checks in spec §6 (lines 950–1163) pass.

## Global Constraints

**Every task's requirements implicitly include this section.** Carried from MVP 1 spec §1 and restated in MVP 2 spec lines 38–51.

1. **Read-only external access.** A correction or erasure request is a human workflow, never an API write into a customer's system. The GET-only HTTP client stays.
2. **Zero code dependency** between `/dpdp-platform` and `/demo-company-server`, in either direction.
3. **Tenant isolation via the Prisma extension, never a hand-written `where`.** Every new model must be bucketed in `src/common/tenant/tenant-scoped-models.ts`. `tenant-scoped-models.spec.ts` fails the build if a schema model is unaccounted for — that test is the enforcement.
4. **No legal value hard-coded. Ever.** No bare `90`, `72`, `48`, `30`, `24`, `12`, `7`, `3` tied to a day/hour/month/year/deadline/due/retain in any service. Legal periods live in `ComplianceRule` rows with a citation and a basis. The single sanctioned exception already in the codebase is `AGE_OF_MAJORITY_YEARS = 18` in `src/modules/identity/age.service.ts` (s.2(f)). Check 1 (spec line 952) is the grep that enforces this.
5. **Every state change writes an `AuditEvent`** via `AuditService.record(tx, …)`, inside the caller's own transaction. New action strings are appended to the `AUDIT_ACTIONS` literal union in `src/common/audit/audit-actions.ts` (currently 36 values).
6. **UTC in the database (`@db.Timestamptz(6)`), organisation timezone at render**, converted exactly once via `formatInOrgTimezone`.
7. **The platform never concludes.** Every generated notice is a draft until a human with the right permission approves it. Every seeded legal value shows its citation and an "unreviewed" badge until the DPO confirms it. **No screen says the company "is compliant."**
8. **Compliance messaging and marketing never share a code path.** A breach notice reaches everyone affected regardless of consent. A promotion reaches only those who granted consent for that purpose, and never reaches a child. (Spec line 50 — the one rule new to MVP 2.)
9. **Never write `DENIED` because evidence is missing.** Absence of evidence is `UNKNOWN`, forever, until the person says otherwise. (Spec line 643 repeats this because agents get it wrong.)
10. **Permission enforcement is `@RequirePermission('CAN_X')`.** A role-name comparison used for authorization (`if (role === 'DPO')`) must not appear anywhere.

## Wave Discipline — how parallelism actually works here

The human partner requires maximum parallelism. Superpowers' default is one implementer at a time; MVP 1's own journal records the two ways that goes wrong. Both are designed out here rather than hoped away:

- **Six parallel Sonnet implementers exhausted the rate limit; four survived.** → **Hard cap of four concurrent implementers.**
- **Letting parallel agents edit `router.tsx`, or letting them commit, caused conflicts.** → **No parallel agent touches a shared file, and no parallel agent commits.**

### The rules every wave obeys

1. **Exclusive file ownership.** Each parallel task owns a disjoint set of directories. Two tasks in the same wave never write the same file.
2. **Shared files belong to the integrator, nobody else.** The shared-file list is exactly: `backend/prisma/schema.prisma`, `backend/src/app.module.ts`, `backend/src/common/audit/audit-actions.ts`, `backend/src/common/tenant/tenant-scoped-models.ts`, `backend/prisma/seed.ts`, `frontend/src/router.tsx`, `frontend/src/components/shared/AppShell.tsx`, `frontend/src/principal/components/PortalShell.tsx`, both `package.json`s, `.env*`.
3. **Every parallel backend task creates its own `*.module.ts`** exporting its providers. The integrator's only job in `app.module.ts` is adding it to `imports`.
4. **Every parallel frontend task exports its pages from its own directory.** The integrator's only job in `router.tsx` is adding the `<Route>` and the nav entry.
5. **The integrator is a single sequential Sonnet subagent** at the end of each wave. It wires the shared files, runs the full build + both test suites, fixes only integration breakage, and makes the wave's commits.
6. **Review is per wave, not per task** (human partner's decision). After the integrator commits, one Sonnet reviewer reads the whole wave's diff against the spec slices the wave covers. Findings enter the standard SDD fix loop (max 5 rounds), dispatched to a fresh implementer scoped to the offending files. The final whole-branch review at the end runs on **Opus**.
7. **Waves are strictly sequential.** Wave N+1 does not dispatch until wave N's integrator has committed and its review is clean or its findings are parked with rulings.
8. **Dispatch hygiene.** Each implementer receives: one line on where its task fits, the path to its task brief (generated by `scripts/task-brief`), the interfaces published by earlier waves' reports, and its report-file path. It never receives this plan file, prior task summaries, or another agent's report.

### Interface publication

Because tasks in the same wave cannot read each other's code, every implementer's report **must** open with an `## Interfaces published` section listing exported symbols, their signatures, route paths, and DTO shapes. The orchestrator copies those verbatim into the next wave's dispatches. A task that consumes a sibling's data does so **through Prisma models created in Wave 0**, never through a sibling's service class.

## Rulings taken up front

The orchestrator records these in the ledger before Task 1 dispatches. Each is a decision made on the human partner's behalf; each names what it costs if wrong.

- **`/api/me/*` route parameters.** MVP 1 has a mechanical guard in `test/principal-portal.e2e-spec.ts` that reflects `ROUTE_ARGS_METADATA` off `MeController` and **fails the build if any handler declares `@Param`, `@Query` or `@Body`**. MVP 2's spec (lines 893–898) requires `GET /api/me/notices/:id?lang=`, `GET /api/me/requests/:ref`, `POST /api/me/requests/:ref/cancel`, `PUT /api/me/nomination`. **Ruling:** amend the guard rather than delete it — it must still fail on any parameter that could name a *person* (`principalId`, `dataPrincipalId`, `id` on a principal route), while permitting parameters that name a *resource the principal owns*, every one of which must be re-verified against `@CurrentPrincipal().dataPrincipalId` inside the service before returning anything. The amended guard plus an explicit "cannot read another principal's request by reference" e2e test is a Wave 3 requirement. *Cost if wrong:* an IDOR in the portal — which is why the test is amended, not removed.
- **No shared e2e harness exists.** All 25 MVP 1 specs hand-roll `createOrgWithEmployee`, `ensurePermission`, app bootstrap and cleanup. Twenty-six new tasks each reinventing that is guaranteed drift. **Ruling:** Task 1 creates `backend/test/support/e2e-harness.ts` (new file, zero edits to existing specs) exporting `bootstrapTestApp()`, `createOrgWithEmployee(roleCode, permissionCodes)`, `ensurePermission(code)`, `cleanupOrgs(orgIds)` and `waitUntil(fn, ms)`, transcribed from the existing `rbac.e2e-spec.ts` pattern. Every MVP 2 spec imports it. MVP 1 specs are left untouched. *Cost if wrong:* one file to delete.
- **`AgeStatus` has four values, not three:** `UNKNOWN | ADULT | CHILD | GUARDIAN_REPRESENTED`. **Ruling:** the CH-05 marketing block excludes `CHILD` **and** `GUARDIAN_REPRESENTED` — a guardian-represented principal is by definition one the platform is treating as not self-determining. The spec's pseudocode (line 656) names only `CHILD`; suppressing the wider set is the safe direction and is recorded as a deliberate widening. *Cost if wrong:* an adult under guardianship misses a marketing email.
- **`ConsentEvent` and `RequestEvent` reuse the existing `ActorType` enum** (`EMPLOYEE | PRINCIPAL | SYSTEM`) — spec §2.2 references `ActorType` without redefining it, so it means MVP 1's.
- **Erasure tasks are created by one owner.** Consent withdrawal (spec line 646) must create an `ErasureTask` in the same transaction. To keep that out of two parallel tasks, **Wave 2 builds the retention module first** and publishes `ErasureTaskService.createFromTrigger(tx, {trigger, dataPrincipalId, …})`; **Wave 3's consent task consumes it**. *Cost if wrong:* one extra wave boundary.
- **Campaign guards read tables, not sibling services.** `CampaignService.send()` reads `ConsentRecord`, `DataPrincipal.ageStatus`, `BreachAffectedPrincipal` and `InformationRequest` directly via Prisma. All four models exist from Wave 0, so all eight guards can live in one task with no cross-task service dependency.
- **`RETENTION_INACTIVITY` resolves to `null` when `Organization.thirdScheduleClass = NONE`** (spec lines 569, 621, Check 25). This is a property of `ComplianceService.resolveRule`, not of the retention scan, and is unit-tested there.
- **Frontend UI primitives are promoted, not duplicated.** `frontend/src/fiduciary/components/form-controls.tsx` already holds local `SelectControl`, `TextareaControl`, `CheckboxOption`, `FieldShell`; `@radix-ui/react-dialog` is used inline in `LinkedRecordsPanel.tsx`. **Ruling:** Wave 5 promotes these into `components/ui/{select,textarea,checkbox,dialog}.tsx` and re-points `form-controls.tsx` at them, before any MVP 2 page is written. *Cost if wrong:* a mechanical follow-up refactor.
- **The frontend's stale comment about permissions is wrong, not a bug.** `src/lib/auth.ts` lines 22–27 claim `/auth/employee/me` does not return `permissions`. It does — `employee-auth.controller.ts:155` maps `employee.role.permissions`. `PermissionGate` works today. Wave 5 corrects the comment; no behavioural change.
